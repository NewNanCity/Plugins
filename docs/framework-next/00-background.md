# Background

## 为什么需要新框架

当前 NewNan 插件生态已经不是几个简单 Bukkit 插件的集合。实际业务里长期存在这些需求：

- 插件有多个模块、多个 manager、多个可选依赖。
- 配置、语言、命令、GUI、数据库、网络、缓存都需要 reload 和诊断。
- 事件和任务互相嵌套，例如命令等待玩家点击，事件启动异步加载，GUI 点击触发持久化。
- 生产服务器要控制 tick 成本，不能靠启动真实 server 才发现问题。
- 管理员需要能看懂插件当前状态，而不是只看散乱日志。

旧模式把这些能力分散在 `BasePlugin`、`BaseModule`、各种 manager、helper、YAML 文件和命令注册器里。它能工作，但心智负担高，边界不稳定，错误常常要在运行服排查。

新框架的价值不是“少写几行 Bukkit 代码”，而是把重复且高风险的运行时责任收进框架，让插件作者只表达业务意图。

## 生产基线

新框架的第一版本必须服务当前生产现实：

- Minecraft / Paper: 至少覆盖 1.20.1+。
- Java runtime: 产物字节码目标 Java 17。
- Kotlin: 使用稳定版本，JVM target 对齐 Java 17。
- NMS: 第一阶段不依赖 NMS 或 CraftBukkit internals。
- Paper newer versions: 可以做 adapter 优化，但不能让核心 API 依赖 1.20.5+ 专属行为。
- Folia: 中期目标，近期只在 affinity 和 owner 模型里预留。

## 重写边界

后续会新开干净项目从头做。这个设计包默认：

- 不继承旧源码入口。
- 不从旧模块 re-export 类型。
- 不以当前实现是否已经写过作为判断依据。
- 不把“适配旧代码”作为第一阶段目标。
- 不讨论旧插件迁移路径。

旧仓库仍有价值，但只用于需求考古：

- 哪些业务需求是真实存在的。
- 哪些痛点反复出现。
- 哪些模式是反面教材。
- 哪些测试和样例可以作为验收思路。

## 开发者体验原则

普通插件作者的第一屏应该是自然、简洁、可读的业务声明：

- 插件声明像描述插件本身。
- 配置是 Kotlin data class。
- 文本是 typed interface。
- 命令字符串直接展示玩家看到的命令形态。
- 参数、校验、补全、权限和帮助在同一个命令块里声明。
- 事件写在模块附近，默认绑定模块 owner。
- 任务从当前作用域派生，不手动保存裸 `BukkitTask` 或 `CoroutineScope`。
- GUI 写成 screen/page/slot，而不是 Inventory listener 拼装。

底层复杂性必须保留，但放在内部和高级文档里。
